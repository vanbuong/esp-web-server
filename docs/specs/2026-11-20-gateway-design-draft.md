# ESP32 Provisioning + HTTPS/mTLS Gateway Web Server (ESP-IDF)

## Context
Learning project, starting from an empty folder (`C:\Working\Learn\esp32\web-server`). Goal: a gateway firmware that
1. on first boot opens a SoftAP with an HTTP (plain) web UI and a default login,
2. advertises itself via mDNS as `gatewayXXXX.local` (XXXX = device id),
3. walks the user through provisioning: forced password change → Wi-Fi scan/select/connect → upload TLS material,
4. reboots into station mode and serves **HTTPS only**, with a Kconfig choice between
   **server-auth TLS** (browser checks device) and **mutual TLS** (device also requires a client certificate signed by our CA),
5. ships with cert-generation scripts and docs explaining the PKI best practice.

Framework: **ESP-IDF v5.4+** (v6.x for newer chips, see Targets). Deliverable: full project + scripts + README docs.

## Targets (sdkconfig.defaults per target)
| Target | Notes |
|---|---|
| `esp32` | Base; mbedTLS buffers tuned small (`MBEDTLS_SSL_IN_CONTENT_LEN` 4096 + variable buffer), 1 TLS session max |
| `esp32` + PSRAM | Separate profile `sdkconfig.defaults.esp32_psram` (`SPIRAM=y`, `MBEDTLS_EXTERNAL_MEM_ALLOC=y`), allows 2–3 sessions |
| `esp32s3` | Standard, PSRAM optional |
| `esp32s31` | New chip — verify ESP-IDF branch that supports it at implementation time (likely v6.x / master); keep target-specific code zero so it's just a defaults file |
| `esp32p4` + `esp32c6` | P4 has **no radio**: Wi-Fi via C6 co-processor using `esp_wifi_remote` + `esp_hosted` (managed components). Same `esp_wifi_*` API in app code; C6 runs esp_hosted slave firmware (documented flash step) |

Build selection: `idf.py set-target <t>` + `SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.defaults.<profile>"`. A `build_all.ps1` script builds every profile to catch breakage.

## Kconfig options (`main/Kconfig.projbuild`)
- `GW_HOSTNAME_PREFIX` = "gateway"; `GW_DEVICE_ID_SOURCE`: MAC last 2 bytes (hex, default) | fixed value
- `GW_AP_SSID_PREFIX` = "Gateway-Setup-", `GW_AP_PASSWORD` (empty = open; default WPA2 "setup1234"), `GW_AP_CHANNEL`
- `GW_DEFAULT_USER` = "admin", `GW_DEFAULT_PASSWORD` = "admin" (forced change; min length 8 enforced)
- **`GW_TLS_MODE`** choice: `GW_TLS_SERVER_AUTH` | `GW_TLS_MUTUAL` (default mutual)
- `GW_MAX_SESSIONS`, `GW_SESSION_TIMEOUT_MIN`, `GW_FACTORY_RESET_GPIO` (default BOOT pin per target)

## Boot state machine (`main.c`)
```
nvs init → dev_id → storage.load()
if !provisioned:        PROVISIONING mode
    wifi_mgr AP+STA (APSTA, so scan & connect-test work while AP is up)
    mdns gatewayXXXX.local (_http._tcp:80)  + captive-ish redirect of / to /login
    web_prov HTTP :80
else:                   OPERATIONAL mode
    wifi_mgr STA connect (retry/backoff; after N failures → fall back to AP provisioning? → Kconfig, default: stay retrying, factory reset via button)
    mdns gatewayXXXX.local (_https._tcp:443)
    web_secure HTTPS :443 (+ port 80 → 301 redirect to https)
```

## Provisioning flow (HTTP, AP mode)
Wizard enforced server-side by a `prov_step` stored in NVS (can't skip steps by URL):
1. `POST /api/login` default creds → session cookie (`HttpOnly; SameSite=Strict`).
2. `POST /api/password` — must change; new hash stored (PBKDF2, random 16B salt, 10k iterations); default creds then invalid.
3. `GET /api/wifi/scan` → JSON list (ssid, rssi, auth, channel; dedup, sorted). `POST /api/wifi/connect` {ssid, password} → test connect in STA while AP stays up, return got-IP or error; save on success.
4. `POST /api/certs` multipart/raw PEM upload of: **server cert (chain)**, **server private key**, **CA cert** (CA required for mTLS mode; used to verify client certs). Device validates: PEM parses (mbedtls_x509_crt_parse / mbedtls_pk_parse_key), key matches cert (`mbedtls_pk_check_pair`), cert SAN contains `gatewayXXXX.local`, cert chains to uploaded CA, not expired (warn only — no RTC time yet; SNTP not available in AP mode).
5. `POST /api/finish` → set `provisioned=1` → response → `esp_restart()` after 2s.

## Operational HTTPS server (`web_secure`)
- `httpd_ssl_config_t`: `servercert` + `prvtkey_pem` from NVS; in **mutual** mode also `cacert_pem` → esp_https_server sets `MBEDTLS_SSL_VERIFY_REQUIRED`, so a browser without a valid client cert fails the handshake and never sees a page.
- `user_cb` hook logs client cert subject CN (and optionally enforces an allow-list of CNs / serials — stretch).
- Then app-level login with the user's changed password (defense in depth: cert = "which device/PC", password = "which human").
- SNTP started after STA connect so cert expiry checks are meaningful.
- Pages: login, dashboard (device info, IP, RSSI, uptime), change password, replace certs, factory reset (requires password re-entry).

## Security notes baked in
- Never store plaintext password; constant-time compare.
- Login rate-limit (e.g. 5 fails → 30s lockout).
- Private key in NVS: document enabling **NVS encryption + flash encryption + secure boot** for production (off by default for learning, Kconfig/sdkconfig notes in docs).
- Default AP + HTTP is a known weak window: documented; option for per-device AP password printed on label.

## PKI — answer to question 5 (goes into `docs/PKI.md` + `tools/pki/`)
**Yes, you need three kinds of material, but with different owners:**
| Item | Generated where | Lives where | Notes |
|---|---|---|---|
| **Root CA** key + cert | Your PC / offline machine, once | CA key kept **offline, never on device**; CA **cert** goes to every device and every client browser/OS trust store | ECDSA P-256, 10 yr |
| (optional) Intermediate CA | Signed by root | Used for day-to-day signing so root can stay offline | recommended for real products |
| **Server** key + cert | One per device | Uploaded to that device | SAN = `DNS:gatewayXXXX.local` (+ optional IP), EKU `serverAuth`, 1–2 yr. Browsers need SAN, CN is ignored |
| **Client** key + cert | One per user/PC (only for mTLS mode) | Imported into browser/OS as **.p12** (password protected) | EKU `clientAuth`, CN = user/PC name, revoke by removing CA or via CN allow-list |

Best practices covered in docs: ECDSA P-256 (much faster TLS handshake on ESP32 than RSA-2048), unique cert per device (never a shared key), short-ish validity, root CA offline, the better alternative of **on-device key + CSR** (private key never leaves the ESP32 — documented as stretch goal since requirement is upload), and how to trust the CA in Windows / browsers.
Scripts (OpenSSL, PowerShell + bash): `make_ca` → `ca.key/ca.crt`; `make_server -Id 1234` → `gateway1234.key/.crt`; `make_client -Name laptop1` → `laptop1.p12`.

## Verification
1. `tools/build_all.ps1` builds all 5 profiles cleanly.
2. On hardware (esp32 first): fresh flash → join `Gateway-Setup-1234` → `http://gateway1234.local` (and `192.168.4.1` fallback) → login admin/admin → forced password change → scan shows APs → connect succeeds → upload certs generated by scripts; bad key/cert mismatch rejected → reboot.
3. Station mode: `ping gateway1234.local`; `curl --cacert ca.crt https://gateway1234.local` → in mutual mode handshake fails; with `--cert laptop1.crt --key laptop1.key` → login page. Browser: without .p12 → connection error; with .p12 imported → prompt to pick cert → login.
4. Server-auth mode build: browser with CA trusted shows padlock, no client cert asked.
5. Factory reset button → back to AP provisioning.
6. P4+C6: flash esp_hosted slave on C6, verify scan/connect work through `esp_wifi_remote`.
