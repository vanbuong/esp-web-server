# Plan 2 — PKI, TLS Identity, HTTPS Normal Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish the setup wizard (device key + CSR or key upload, validated, then finish/reboot) and boot provisioned devices into station mode with an HTTPS-only admin API, server-auth or mutual TLS chosen in Kconfig — plus the PKI scripts that make all the certificates.

**Architecture:** New pure logic in `gw_core` — `gw_tls_check` (validate key/cert/CA against the rules) and `gw_tls_csr` (ECDSA P-256 key + CSR) — host-tested with fixtures the PKI scripts generate at test time. `gw_store` gains one atomic TLS record plus a pending key. `gw_http` is split into shared handlers (`/api/status`, login, logout), the setup server (adds TLS + finish steps) and a new HTTPS admin server; a tiny HTTP server on :80 only redirects. `gw_net` gains station mode with backoff and SNTP. `main.c` picks the mode.

**Tech Stack:** ESP-IDF v6.1.1 (`esp_https_server`, mbedTLS 4.1.1 / PSA, `esp_netif_sntp`), OpenSSL CLI (1.1.1 in Git for Windows, 3.0 in WSL) via bash scripts, Unity host tests in WSL, Python 3.12 stdlib (`ssl`, `http.client`) for the HTTPS smoke test.

**Spec:** `docs/specs/2026-11-20-gateway-design.md` — sections 5, 7.2 (normal mode), 7.3 steps 4–5, 7.4, 7.7, 7.9, 7.10, 7.12. Roadmap: `docs/plans/2026-11-20-roadmap.md` (plan 2). Builds on plan 1 (merged, `main` @ 34f5e86).

**Targets affected:** esp32 only (other profiles are plan 5).

## Global Constraints
- Keys: ECDSA P-256 everywhere the scripts or device generate one. Upload path accepts any key mbedTLS parses (EC or RSA ≥ 2048).
- Device cert: SAN `DNS:gatewayXXXX.local` (exact, case-insensitive compare), EKU must allow `serverAuth` (absent EKU = allowed), validity 2 y. Client certs: EKU `clientAuth`, CN = person/PC, exported as password-protected `.p12`. Root CA: 10 y, its key never leaves the PC.
- One root CA signs device and client certs. Uploaded `ca` = trust anchor (root); uploaded `cert` may be a chain (device + intermediate).
- Certificate dates are never checked on the device (`CONFIG_MBEDTLS_HAVE_TIME_DATE` stays off); expiry is only displayed once SNTP has set the clock.
- CSR path: the private key is generated on the device and never leaves it (no endpoint ever returns a private key).
- TLS mode: Kconfig choice `GW_TLS_MODE_MUTUAL` (default) | `GW_TLS_MODE_SERVER_AUTH`. Mutual = `cacert_pem` given to `esp_https_server` → browsers without a CA-signed client cert fail the handshake. Any client cert signed by the CA is accepted; its CN is logged and returned by `/api/status`.
- Once PROVISIONED: no setup endpoints exist; port 80 only answers `301` to `https://<hostname>.local<same path>`; admin API only on 443. Session cookie adds `Secure`.
- Request body limit: 512 bytes, except TLS upload endpoints: 8192 bytes.
- NVS keys are records written atomically (one key each): `tls` (key+cert+ca), `tls_pend` (pending key PEM). Data saved before any step/state change.
- No secrets in logs: private keys, passwords, PSKs, tokens, `.p12` passwords. Certificates and CNs may be logged.
- Generated PKI material goes to `tools/pki/out/` and `test/host/fixtures/` — both git-ignored; no key or `.p12` is ever committed (host-test fixtures are regenerated by `tools/wsl/host_test.sh`).

## Review Focus
1. PEM in the wild: CRLF line endings, missing trailing newline, leading/trailing whitespace, device+intermediate chain in `cert`, PKCS#8 vs SEC1 EC keys, RSA-2048 key → accepted or rejected exactly per the rules (Task 3 tests).
2. Wrong material: cert for another hostname, cert whose EKU is only `clientAuth`, cert signed by a different CA, key not matching cert, device cert uploaded as `ca`, empty strings, garbage → specific error codes, nothing stored (Tasks 3, 6).
3. Power loss: device never boots PROVISIONED without a complete `tls` record; finishing without one is refused (Tasks 5, 6).
4. Mutual-TLS handshake failures (no cert, wrong-CA cert) repeated 20× → server keeps serving valid clients, free heap returns to its baseline (Task 8 hardware check).
5. Renewing the identity in the admin API: generating a new CSR keeps the current HTTPS identity working until a matching cert is uploaded; a cert that doesn't match the pending key is rejected (Task 9).

### Task 2: Bigger NVS partition

**Files:** Modify `partitions.csv`, `test/host/partitions.csv`, `docs/ARCHITECTURE.md` (flash table).

Why: the TLS record (key + cert chain + CA, up to ~6 KB) plus a pending key does not fit comfortably in 24 KB of NVS, which also needs a free page to rewrite records. Changing the layout now is free (no devices deployed); later it would need a migration.

```
nvs_keys,  data, nvs_keys, 0x18000,  0x1000,   encrypted
factory,   data, nvs,      0x19000,  0x3000,
ota_0 ... coredump: unchanged
```

### Task 3: Certificate validation (`gw_core/gw_tls_check`)

**Files:** Create `components/gw_core/include/gw_tls_check.h`, `components/gw_core/gw_tls_check.c`, `test/host/main/test_tls_check.c`; test app embeds fixtures (`EMBED_TXTFILES` from `test/host/fixtures/`).

**Interfaces:**
```c
#define GW_TLS_PEM_MAX 4096   // per field
typedef struct {
    char subject_cn[64];
    char issuer_cn[64];
    char not_after[20];       // "YYYY-MM-DD HH:MM:SS" (UTC) as written in the cert
    char key_type[12];        // "EC P-256", "RSA 2048", ...
} gw_tls_info_t;

/**
 * Checks a server identity before it is stored. Returns NULL if OK (info filled), else a stable
 * error code string: "bad_key" | "bad_cert" | "bad_ca" | "key_mismatch" | "wrong_name" |
 * "not_server_cert" | "not_signed_by_ca". Dates are not checked.
 */
const char *gw_tls_check(const char *key_pem, const char *cert_pem, const char *ca_pem,
                         const char *hostname, gw_tls_info_t *info);

/** Normalizes PEM in place: CRLF→LF, trims surrounding whitespace, ensures one trailing '\n'. */
void gw_pem_normalize(char *pem);
```
Rules in order: parse key (`mbedtls_pk_parse_key`, length incl. NUL) → `bad_key`; parse cert chain → `bad_cert`; parse CA → `bad_ca` (also `bad_ca` if the CA cert is not `CA:TRUE`); `mbedtls_pk_check_pair(&crt->pk, &key)` → `key_mismatch`; first cert's SAN must contain `DNS:<hostname>.local` → `wrong_name`; `mbedtls_x509_crt_check_extended_key_usage(crt, OID serverAuth)` → `not_server_cert`; `mbedtls_x509_crt_verify(crt, ca, NULL, NULL, &flags, NULL, NULL)` → `not_signed_by_ca`.
